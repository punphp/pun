### Perf rounds

Each round's pun cells come from `BENCH=analyse TOOLS=pun scripts/bench.py <project>` (same settings: 3 runs after
1 warmup, `HEAVY_EXCLUSIVE=1`), the old and new binaries run back to back per project. The reported errors (file,
line, identifier, message, tip) are byte-identical before and after on all five projects.

| project | round 0 | round 1 | wall | rss |
|---|---:|---:|---:|---:|
| pinkary | 1.09 s, 832 MB | 0.53 s, 882 MB | -51% | +6% |
| larastan (v3.10.0) | 0.63 s, 585 MB | 0.30 s, 542 MB | -52% | -7% |
| laravel-framework | 1.53 s, 1127 MB | 0.63 s, 1112 MB | -59% | -1% |
| pest | 0.46 s, 502 MB | 0.25 s, 446 MB | -46% | -11% |
| laravel-pint | 0.47 s, 399 MB | 0.22 s, 346 MB | -53% | -13% |

(Round 0 re-measured here: the table's first pun column was 1.06/0.58/1.81/0.68/0.52 s on the earlier run.) Per
change, A/B with `/usr/bin/time` on pinkary, laravel-framework and laravel-pint:

- round 1: walk directories and Composer's autoload sources in parallel, using readdir's entry type instead of a stat
  per entry; scan in 32-file rayon chunks (with one contiguous chunk per thread, threads sat idle for about half the scan)
  merged in file order, beside the prelude build; build the prelude once instead of a static copy plus its clone;
  Mago's parallel populator; check analysed files in parallel; drop the codebase off the critical path. Wall -36 to
  -55%, rss -2 to -5%.
- round 1: NEON tokens matched without PCRE2's UTF mode, which re-validated the whole input at every token
  (quadratic on PHPStan's own config.neon; config load 45 ms to 9 ms). Wall -3 to -14%, rss 0%.
- round 1: symbols.json read straight into typed structs instead of an order-preserving `serde_json::Value` first
  (half the time, a third of the transient memory, for each of the 8.4 and 8.5 loads). Wall -2 to -25%, rss -5 to -9%.
- round 1: analysed files kept from the scan for the rules (no second read), PHPStan's 8.4 reflection loaded beside
  the scan instead of by the first rule that needs it while the other threads wait, one arena per rayon job. Wall
  0 to -3% (within noise), rss 0%.
- What is left: opening files (about 30 µs per `open()` on this Mac, a quarter of all CPU samples) for the 8-18k
  vendor files scanned eagerly, Mago's parse and scan of them, and Mago's populate (about 15%). Memory is Mago's
  metadata for every scanned vendor file (about 20 KB each live) plus about 30% allocator overhead; neither
  mimalloc nor dropping file signatures moved it.

### Lint perf rounds

Each round reruns `BENCH=lint TOOLS=pun RUNS=10 scripts/bench.py pinkary laravel-framework` under
`HEAVY_EXCLUSIVE=1`, before and after, and keeps pun-lint's output byte-identical: the `check` problems and the `fix`
output of all 3,376 corpus files (`examples/dump`), and `fix_dir` against `rector process` with the ported rules
(`diff -r` empty on both projects). bench.py polls every 20 ms, which hides most of a 70 ms run, so each change is
also timed with 30 plain spawn-and-wait runs (median; "precise" below).

| round | project | before (bench.py) | after (bench.py) | before (precise) | after (precise) |
|---|---|---:|---:|---:|---:|
| 1 | pinkary | 45.2 ms, 14.4 MB | 44.3 ms, 13.2 MB | 10.2 ms, 14.2 MB | 9.6 ms, 13.7 MB |
| 1 | laravel-framework | 108.4 ms, 83.5 MB | 102.0 ms, 81.8 MB | 80.9 ms, 84.0 MB | 67.0 ms, 82.8 MB |
| 2 | pinkary | 44.0 ms, 13.8 MB | 44.4 ms, 13.8 MB | 9.5 ms, 13.7 MB | 7.5 ms, 13.3 MB |
| 2 | laravel-framework | 100.5 ms, 82.4 MB | 91.5 ms, 81.6 MB | 66.2 ms, 82.5 MB | 53.2 ms, 85.7 MB |

- round 1: the walk writes every report into one list and tags it with its rule ID, instead of a list per node
  drained into the results per rule, which cost an allocation check and a drain on each of ~2.4M nodes. wall -8%
  (laravel-framework, precise), rss 0%.
- round 1: `no-unused-catch-variable` visits only `try` nodes and finds their statement list two ancestors up,
  instead of collecting the statement children of every node. wall -4%, rss 0%.
- round 1: rules name the node kinds they report on (`Rule::targets`, as in Mago's linter) and the engine calls a
  rule only on those kinds; a rule without targets still sees every node. wall -6%, rss -1%.
- round 1 total: laravel-framework wall -17% precise (-6% bench.py), rss -1 to -2%; pinkary wall -6% precise (-2%
  bench.py), rss -4 to -8%; single-thread CPU (`examples/cost`) 67.2 to 40.5 us per file. What is left is Mago's
  parser (about 70% of user time), the tree walk (Mago's `visit_children` on every node, about 25%), and file opens
  (most of the system time). Peak memory is the Mago arenas of the files parsed at the same time; a reused
  per-thread arena did not change wall time and raised peak memory by 9 MB, so it was dropped.
- round 2: `examples/check` (the bench's driver) walks the directories on its worker threads: one stack holds the
  directories still to list and the files still to check, so checking starts with the first directory instead of
  after a single-threaded walk of the whole tree, and an entry's type comes from the directory listing instead of a
  `stat` per entry. The walk alone took 15.7 ms of laravel-framework's 66 ms (9.6 ms without the `stat`s). wall -20%
  precise on both projects (-9% bench.py on laravel-framework; pinkary's 9.5 ms run sits under bench.py's 44 ms
  floor), rss +4% on laravel-framework (the threads start parsing at once; a FIFO stack was +14%) and -3% on
  pinkary (bench.py: -1% and 0%). The engine is unchanged: `check` problems and `fix` output are byte-identical.
- round 2, no change: the engine itself has nothing over 3% left. Single-thread over laravel-framework's sources in
  memory, Mago's parse is 89 ms, parse plus the walk 127 ms, and the full `check` with both rules 127 ms, so the
  rules cost under 1%. The walk (29%) is Mago's `visit_children` on 5.2M nodes; skipping the 1.1M nodes of kinds
  that never have children made it slower (93 vs 78 ms over pre-parsed trees). Opening files is the largest system
  cost (25% of samples, `open` itself): `openat` on a held directory handle and more threads (12, 16, 24) did not
  change wall time. Peak memory is Mago's arenas: the 462 KB `ValidationValidatorTest.php` takes a 26 MB arena
  (39k 376-byte allocations make 14.7 MB), so one thread alone peaks at 36 MB; only a change in Mago's parser
  would cut it.
