# Rust code audit prompt

Paste everything below the line into a fresh agent session at the repo root. It is the Rust version of the general
code-smell audit, tuned for Pun: what clean, idiomatic Rust looks like, which of Pun's odd-looking patterns are
deliberate, and how to prove each finding. It writes a tracker and changes no code.

---

You are auditing the Rust workspace in the current working directory for code smells, unidiomatic Rust and
architectural problems. The goal is an audit the maintainers can act on, so that once every item lands the code reads
as plainly as the problem allows: small functions with honest names, types that make wrong states impossible, errors
that say what went wrong, and no code that exists for no reason. Every finding must be real, verified against the
current tree, and not already tracked.

Inputs. Use these defaults unless the user overrides them:

- Tracker file: `context/AUDIT.md`. Create it if it is missing; append to it if it exists.
- Scope: first-party Rust under `crates/*/src`, `crates/*/tests`, `crates/*/build.rs`, and the workspace and crate
  `Cargo.toml` files. Exclude generated code (`crates/pun-format/src/php_grammar.rs`, anything whose header says
  "Generated by" or "Do not edit"), JSON and text fixtures, `corpus/`, `docs/`, `design/`, `.oracle/`, `target*/`.
- Changes allowed: the tracker file only. Don't edit source, tests, `Cargo.toml` or CI, and don't commit.

## Before you start

Learn the project before judging it.

1. Read `AGENTS.md` in full, then `context/README.md`, `context/PLAN.md`, `context/plan/foundations.md`,
   `context/REQUESTS.md`, `context/reference/tokens.md` and `context/reports/COVERAGE.md`.
2. Read the root `Cargo.toml` (workspace dependencies, profiles, any `[workspace.lints]`), every crate's `Cargo.toml`,
   `.github/workflows/ci.yml`, and any `rustfmt.toml`, `clippy.toml` or `rust-toolchain.toml`. Note every `#[allow]`,
   `#[expect]` and `#![allow]` in the tree (`rg -n '#!?\[(allow|expect)' crates`). Each one is a deliberate choice;
   read its reason before you flag nearby code.
3. Run `git log --oneline -20` and `git status`, and `ps aux | grep -E 'cargo|rustc|php'` to see what other agents are
   building. Trust only what you read in this session.
4. If the tracker exists, read it in full. Everything in it, including won't-do and rejected items and their reasons,
   is out of scope. Don't re-report it in other words.
5. Respect the machine budget in `AGENTS.md`: `source ~/.cargo/env`, `export CARGO_BUILD_JOBS=1`, your own
   `CARGO_TARGET_DIR` (for example `target-audit`), `timeout 900 nice` in front of every cargo command, one cargo
   command at a time, in the foreground. Subagents never run cargo; only you do.

### Pun's deliberate conventions

These are design decisions, not smells. Confirm each against the code and the guidance files, add any others you find,
and report code that breaks them.

1. **Ports stay traceable to upstream.** Fixers and analyzers port PHP-CS-Fixer, Pint or PHPStan function by function,
   keep upstream names in snake_case (`get_indent`, `is_token_kind_found`, `get_declarations_from_tokens`), carry a
   `//! Port of ...` header, and often keep upstream's index loops and branch order. So `get_` prefixes, index-based
   `while` loops and PHP-shaped control flow are fine where they mirror upstream. Flag them only where the Rust code
   has drifted from upstream with no reason given, or where a helper traces to nothing upstream and duplicates
   another.
2. **PHP strings are bytes.** Source text, token content and patterns are `Vec<u8>` and `&[u8]`, and PHP string
   functions go through `pun_tokens::php_compat` (byte `strlen`, ASCII-only `strtolower`, `ltrim_chars`). Flag the
   opposite: `String`, `str::to_lowercase`, `chars()` or UTF-8 assumptions where PHP's behaviour is byte-based.
3. **`preg_*` goes through PCRE2** (`crates/pun-fixers/src/analyzers/preg.rs`). Flag `regex`-crate use or hand-written
   matching that stands in for a `preg_*` call upstream makes.
4. **Output is fixed by upstream.** Messages, exit codes and output bytes must match the pinned tool. Don't propose
   rewording an error that upstream prints verbatim; do flag a message that no longer matches upstream.
5. **One file per fixer, dynamic dispatch.** Each `src/fixers/<name>.rs` exposes `pub fn fixer() -> Box<dyn Fixer>`
   and `build.rs` registers it. `Box<dyn Fixer>` and the `Fixer` trait's default methods are the extension point;
   don't propose generics or an enum in their place.
6. **Speed and memory come first** (benchmarked against Pint and Mago in `scripts/bench.py`). Dense jump tables,
   caches and `thread_local!` regex caches can be deliberate. A readability fix must not add an allocation or a clone
   to a per-token or per-file hot path; say so when a fix touches one.
7. **Mago crates are pinned at `=1.57.0`** and their types appear in Pun's APIs on purpose.
8. **Tests follow AGENTS.md:** 100% line coverage, expected values from an oracle or by hand, no snapshot or
   self-comparison tests. Lines no test reaches should be deleted, not excluded.
9. **Each crate has one owning agent.** A fix that spans crates is fine to report; mark it `Spans crates.` so it can
   be split into `context/REQUESTS.md` items.

Then map the structure: each crate, what it depends on, its public API (`pub` items reachable from `lib.rs`), its
entry points (`pun` subcommands in `pun-cli`, `Fixer` impls, analyse rules), and its size (`wc -l` per file).

## What to look for

Read the checklist as a set of questions, not a list of banned constructs. Clippy already enforces its default groups
in CI, so the value here is in what a linter can't judge: whether a type, a function or a module is the right shape.

### 1. Classic smells, in Rust terms

Check the code against the refactoring.guru catalog, translated to Rust:

- **Bloaters.** Long Function (a function that needs comments to mark its phases), Large Module (a file that holds
  several unrelated concerns; `pun-phpstan/src/types.rs` and `pun-analyse/src/rules/mod.rs` are the first places to
  look), Primitive Obsession, Long Parameter List (more than about four, or several of the same type in a row), Data
  Clumps (the same three arguments passed together through a call chain: a struct waiting to be born).
- **Type-switch abusers.** `match` or `if` chains on a string, an integer tag or `Kind` that are repeated in several
  places and must all change when a variant is added. Struct fields that are `Option` because they are only set in
  one phase (Temporary Field). Trait impls that leave half the methods as no-ops (Refused Bequest).
- **Change preventers.** Adding one rule, preset, reporter or config key that needs edits in several named files
  (Shotgun Surgery). One module that changes for unrelated reasons (Divergent Change). PHP's `Abstract*Fixer`
  inheritance ported as parallel module families (`analyzers/abstract_*`): check that the shared part lives in one
  place and the variants only add what differs.
- **Dispensables.** Dead code (`pub` items no one uses, `#[allow(dead_code)]`, branches no input reaches), duplicate
  code (the same helper in two crates or two fixers), comments that restate the code or describe what it used to do,
  speculative generality (a generic or trait with one user, a config knob nothing sets), lazy wrappers that only
  forward.
- **Couplers.** Feature Envy (a function that mostly calls methods on another crate's type), Inappropriate Intimacy
  (reaching into another type's `pub` fields to keep its invariants by hand), Message Chains, Middle Man.

### 2. Ownership, borrowing and allocation

- `.clone()`, `.to_vec()`, `.to_owned()` or `.to_string()` used to quiet the borrow checker where a borrow, a
  reordering of statements, `std::mem::take`, or splitting a struct borrow would do.
- Parameters typed `&String`, `&Vec<T>`, `&Box<T>` or `&PathBuf` instead of `&str`, `&[T]`, `&T` or `&Path`; owned
  `String` or `Vec` parameters the function only reads; functions that take ownership and hand it straight back.
- Return types that force an allocation the caller then throws away: `Vec<T>` returned only to be iterated once
  (return `impl Iterator`), `String` returned only to be compared, `collect()` followed immediately by `.iter()`.
- `Rc<RefCell<T>>` or `RefCell` inside `&self` methods used as a garbage collector or to hide mutation. Interior
  mutability is fine for a cache the caller can't observe (the `Tokens` block cache is one, and says so); it is a
  smell when it lets logic mutate shared state behind an `&` reference.
- `Arc` where nothing crosses a thread, `Box` around a value that is already small or already on the heap.
- `Cow` missing where a function usually returns its input unchanged, or present where it only adds noise.

### 3. Types that carry meaning

- **Primitive obsession.** Token indices, byte offsets, line numbers and priorities passed around as bare `usize` or
  `i32`, so an offset can be passed where an index belongs. Suggest a newtype only where values of different meaning
  actually get mixed or where an invariant needs guarding; don't wrap every integer.
- **Booleans as modes.** Functions taking one or more `bool` flags (`f(tokens, true, false)`), and `Option<bool>`.
  An enum with named variants reads at the call site (API Guidelines C-CUSTOM-TYPE).
- **Sentinels.** `-1`, `0`, `usize::MAX` or an empty string standing for "none" where `Option` says it.
- **Stringly typed code.** Rule names, presets, reporter formats, NEON or config keys matched as `&str` in more than
  one place, instead of parsed once into an enum (with `FromStr` and `Display`) at the edge.
- **Representable illegal states.** Parallel `Vec`s that must stay the same length, struct fields where some
  combinations are invalid, `pub` fields on a type with invariants (C-STRUCT-PRIVATE). Make the bad state impossible
  to build.
- **Casts.** `as` between integer types where a value can truncate or wrap (`i64 as usize`, `usize as u32`). Use
  `From` where it can't fail, `TryFrom` where it can, and keep `as` for the cases that are obviously in range.
- **Missing standard traits.** Bespoke `new_from_str`, `to_str`, `is_empty_value` or `print` methods where `FromStr`,
  `Display`, `From`, `Default` or `Debug` would let the type work with the rest of std (C-COMMON-TRAITS, C-CONV).

### 4. Errors and panics

- `.unwrap()` and `.expect()` in non-test code. A panic is right for a broken invariant (a programming bug), and then
  `expect("why this can't fail")` should say what invariant held. It is wrong on anything a user controls: file
  contents, paths, `pun.toml`, `pint.json`, NEON, environment variables, subprocess output. Trace each one in
  `pun-cli`, `pun-config`, `pun-phpstan` and `pun-delegate` back to its input.
- Errors swallowed: `.ok()`, `let _ =`, `unwrap_or_default()`, `filter_map(Result::ok)` on a result whose failure
  the user should hear about.
- `Result<T, String>` and ad-hoc `Error(pub String)` types; errors matched by their message text; error types with
  no `Display` or `std::error::Error` impl. Within one binary `anyhow` is fine at the edges (Microsoft guideline
  M-APP-ERROR); a typed error is worth it only where a caller branches on the kind. Say which callers would branch.
- Context lost on the way up: `?` on an I/O error with no `.with_context(|| path)` so the user sees "No such file"
  without the file.
- `std::process::exit`, `panic!` or printing (`println!`, `eprintln!`) deep inside library crates instead of
  returning to `pun-cli`, which owns output.
- `catch_unwind` used for control flow rather than as a last-resort guard.

### 5. Control flow and iterators

- Nesting more than about three levels where `let ... else`, an early `return`, `?` or `continue` would flatten it.
- `if let Some(x) = a { if let Some(y) = b { ... } }` chains that `let` chains (edition 2024) or a `match` on a tuple
  would express directly.
- Manual loops that are `iter().any`, `position`, `find_map`, `rev().find`, `windows`, `chunks` or `retain`, where
  the loop isn't mirroring upstream (convention 1). And the opposite: iterator chains so long or so clever that a
  plain loop would read better.
- `match` on a `bool`, `match` arms that repeat the same body (`A | B =>`), `if x == A || x == B || x == C` where
  `matches!` reads better, `Option` combinator chains (`map_or_else(...).and_then(...)`) less clear than a `match`.
- Index arithmetic that can underflow (`i - 1` on a `usize` with no guard) or go out of bounds.

### 6. Traits, generics and dynamic dispatch

- A trait with one implementation and no plan for a second; a generic parameter with one instantiation.
- `dyn Any` and downcasting used to smuggle a type across a crate boundary (`Tokens` keeps a `dyn Any` cache for a
  `pun-fixers` type). Check whether a generic, a trait or moving the type would remove the downcast.
- `Deref` implemented to fake inheritance (a known Rust anti-pattern), and wrapper types that forward every method.
- Default trait methods that most implementors override, or that implementors must remember to call.
- Generic bounds repeated on every function instead of once on the impl; `where` clauses that restate what the type
  already guarantees.

### 7. Modules, visibility and crate boundaries

- `pub` items not reachable from outside their crate, which should be `pub(crate)` or private (rustc's
  `unreachable_pub`). Items reachable through two paths (glob re-exports, `pub use` of a module and its contents).
- Grab-bag modules (`utils.rs`, `helpers.rs`, `php_functions.rs`) whose contents belong next to their single caller,
  or that duplicate `pun_tokens::php_compat`.
- Dependency direction: lower crates (`pun-tokens`, `pun-config`) must not know about higher ones (`pun-fixers`,
  `pun-cli`). Workarounds for a wrong direction (type erasure, callbacks, string keys) are findings.
- The same concept defined twice across crates (two `Version` types, two path normalizers, two diff printers).
- Very large files. Size alone is not a finding; a file that holds several concerns which change separately is.

### 8. `unsafe`, FFI and global state

- Every `unsafe` block needs a `// SAFETY:` comment saying which invariant makes it sound, and should sit inside a
  small safe wrapper rather than at call sites. Check `analyzers/preg.rs` (PCRE2 FFI and a raw-pointer
  `thread_local!` JIT stack) and `pun-phpstan/src/php.rs` (`libc::fnmatch`).
- `std::env::set_var` and `remove_var` are `unsafe` in edition 2024 because they race with other threads. Tests run
  in parallel threads by default, so any test that sets a variable another test reads is flaky. Prefer passing the
  value in, or a subprocess with `Command::env`.
- `static`, `thread_local!`, `OnceLock` and `LazyLock` state: fine for compiled patterns and tables, a smell when it
  holds configuration or results that make a function's output depend on what ran before.
- `Mutex` or `RwLock` taken in a per-file or per-token loop under `rayon`.

### 9. Performance, only where it is hot

Report a performance smell only with evidence that the code is hot: it runs per token, per file or per rule, or a
profile (`cargo build --profile profiling`, `perf`) shows it. Otherwise prefer the more readable form.

- `format!`, `to_string`, `to_vec` or `Vec::new` inside a per-token loop where a reused buffer or a borrow would do.
- `HashMap` with the default SipHash on small integer keys in a hot loop where a `Vec` indexed by key, or the hasher
  the crate already uses elsewhere, would do. `BTreeMap` used for ordering nobody relies on, or `HashMap` used where
  output order leaks into what the user sees.
- Collections grown one item at a time when the final size is known (`with_capacity`).
- Linear `contains` on a `Vec` inside a loop over the same data.

### 10. Names, comments and docs

- Names that say nothing (`data`, `info`, `tmp`, `handle`, `process`, `Manager`, `Helper`) or that lie (a `get_` that
  mutates, an `is_` that allocates, a `find_` that panics). Ported names from upstream are exempt (convention 1).
- Rust naming rules (RFC 430, C-CASE): `as_` for cheap borrows, `to_` for expensive conversions, `into_` for
  consuming ones; iterator methods `iter`, `iter_mut`, `into_iter`.
- Comments that restate the code, describe old behaviour, or point to a phase or task that has finished. Keep
  comments that explain why: the upstream reference, the PHP quirk, the measured reason for a fast path.
- `pub` items in library crates with no doc comment, or whose first sentence doesn't say what the item is.
- Magic numbers and byte literals with no name or comment saying where they come from.
- `TODO`, `FIXME` and `XXX` with no owner in `context/TASKS.md`.

### 11. Tests

- Tests that fail the bar in `AGENTS.md` (self-comparison, snapshot of current output, no assertion, "does not
  panic" where output is checkable, private helpers already covered through the public API).
- Test helpers copied across crates or test files (fixture loaders, `pun` spawners, temp-dir builders) instead of one
  shared helper per crate.
- Tests that depend on run order, global state or environment variables (see section 8).
- `#[ignore]` without a reason, and `#[should_panic]` without `expected = "..."`.

### 12. Cargo, lints and tooling

- No `[workspace.lints]`: crates can't share a lint policy, and each `#![allow]` is local. Propose one block as a single
  P2 finding, modelled on ruff's and oxc's: `clippy::pedantic` at warn with an explicit allow list, plus chosen
  restriction lints (`dbg_macro`, `print_stdout` and `print_stderr` outside `pun-cli`, `unwrap_used` outside tests,
  `undocumented_unsafe_blocks`, `allow_attributes_without_reason`) and rustc's `unreachable_pub` and
  `unsafe_op_in_unsafe_fn`. Base the allow list on the counts from the tool pass below, not on taste.
- `#[allow(...)]` that should be `#[expect(..., reason = "...")]` so it fails when it stops being needed (Microsoft
  guideline M-LINT-OVERRIDE-EXPECT).
- Crate `Cargo.toml` fields that repeat the workspace instead of `version.workspace = true` and friends; dependencies
  declared in a crate but not in `[workspace.dependencies]`; dependencies no code uses; features enabled that nothing
  needs.
- `build.rs` scripts: `unwrap` is fine there, but check `rerun-if-changed` covers every input.

## Tool pass

Run these once, yourself, before the subagents start, and hand each subagent the output for its slice. Treat the
results as leads. A lint hit is not a finding until it meets the evidence standard and survives the conventions.

```sh
source ~/.cargo/env && export CARGO_BUILD_JOBS=1 CARGO_TARGET_DIR=target-audit && mkdir -p target-audit
timeout 900 nice cargo clippy --workspace --all-targets --message-format=json -- \
  -W clippy::pedantic -W clippy::nursery \
  -W clippy::unwrap_used -W clippy::expect_used -W clippy::panic -W clippy::indexing_slicing \
  -W clippy::undocumented_unsafe_blocks -W clippy::allow_attributes_without_reason \
  -W clippy::print_stdout -W clippy::print_stderr -W clippy::clone_on_ref_ptr -W clippy::as_conversions \
  -W unreachable_pub -W unsafe_op_in_unsafe_fn > target-audit/clippy.json
# Hits per lint, then one `lint file:line` row per hit to split by slice.
jq -r 'select(.reason == "compiler-message") | .message.code.code // empty' target-audit/clippy.json \
  | sort | uniq -c | sort -rn
jq -r 'select(.reason == "compiler-message") | .message | select(.code) as $m
  | $m.spans[] | select(.is_primary) | "\($m.code.code) \(.file_name):\(.line_start)"' target-audit/clippy.json \
  | sort -u > target-audit/clippy-hits.txt
RUSTDOCFLAGS='-D warnings' timeout 900 nice cargo doc --workspace --no-deps --document-private-items
```

If `cargo machete` or `cargo udeps` is installed, run it for unused dependencies; otherwise check each dependency with
`rg` against its crate. Don't install tools.

Use the counts to decide which lints belong in the proposed `[workspace.lints]` allow list (a lint with hundreds of
hits that all follow a convention goes on the allow list; one with a handful of real hits goes to warn). Report a
mechanical lint as one finding with its count and file list, not one finding per hit.

## How to work

Split the in-scope source into slices along crate and module boundaries, each readable in full (about 10k lines).
Recompute sizes with `wc -l`; at the time of writing this split fits:

1. `pun-tokens` and `pun-format` (without `php_grammar.rs`).
2. `pun-fixers/src/analyzers/`, `pun-fixers/src/lib.rs` and `build.rs`.
3. `pun-fixers/src/fixers/` files starting `a` to `h`.
4. `pun-fixers/src/fixers/` files starting `i` to `o`.
5. `pun-fixers/src/fixers/` files starting `p` to `z`, with `pint_laravel_blade/`.
6. `pun-phpstan`.
7. `pun-cli`, `pun-config`, `pun-analyse`, `pun-workspace`, `pun-delegate`, `pun-harness`.

Each slice includes its crate's `tests/` and `Cargo.toml`. Give each slice to a read-only subagent, running in
parallel. Give each one:

- the conventions you wrote down;
- what the tracker already covers;
- this checklist, the evidence standard below, and its slice's clippy and rustdoc output;
- its slice's file list;
- the rule that it must not run cargo, edit files, or post anywhere.

Tell each one to read every file in its slice in full, and to read outside it only for cross-file context (callers,
the trait being implemented, the upstream PHP when the `.oracle/` checkout has it). A slice's findings should be
rooted in that slice. For each fixer it reports on, it should say whether the code still mirrors upstream.

While they run, don't repeat their work. When they report back, verify yourself:

- Open the cited lines for every P0 and P1 finding, and for every claim of dead code, a panic reachable from user
  input, a race, or unsoundness.
- Check runtime claims by running the path: a `pun` command on a small input in a scratch directory, the test that
  covers the path (`cargo test -p <crate> <name>`), or a throwaway test in your scratchpad crate. Check upstream
  claims against `.oracle/` with `scripts/oracle.sh` tools.
- Check dead-code claims with `rg` across `crates/`, `scripts/`, `docs/` and `build.rs`, allowing for `build.rs`
  registration, trait methods called through `dyn Fixer`, serde field names and string lookups in `mapping.toml`.
- Drop findings that don't hold up. Merge the ones several slices found separately, especially duplication and
  shotgun surgery that span crates.

## Evidence standard

A finding is included only if all of these hold:

- It cites `path:line` from the current tree and quotes or names the code.
- It states a concrete consequence: a wrong result or panic (with the input that triggers it), a change that must
  touch several named places, an API that callers will misuse, an allocation on a named hot path, or code that can
  be deleted.
- Dead code has grep proof as above.
- A duplication claim names every copy.
- A suggested fix names the refactoring (Extract Function, Introduce Parameter Object, Replace Type Code with Enum,
  Replace Conditional with Polymorphism, Introduce Newtype, Inline Function, Move Function) or the Rust idiom (`let
  ... else`, `FromStr`, `TryFrom`, `impl Iterator`, `pub(crate)`), fits the conventions, keeps upstream parity, and
  adds no abstraction the problem doesn't need.
- A fix that would change output bytes, a message or an exit code is a bug report against parity, not a cleanup; it
  goes in P0 or not at all.

Fewer findings that are certain are worth more than many that are plausible. Leave out anything that looks wrong but
has a reason (upstream parity, measured performance, Mago's API, a won't-do entry, a comment that explains it). Leave
out a change that only moves code without making anything simpler, unless the unit changes for several reasons at
once. Don't propose new crates, macros or traits unless they delete more code than they add.

## Output

Write the verified findings to the tracker. If it already has a format, match it. Otherwise use this one:

```
# Code Audit

Tick an item when it lands, and note the commit next to it.

- P0: broken today: wrong output, a panic on user input, unsoundness, or a parity break.
- P1: misleading today: an API, name or error that callers or contributors will get wrong.
- P2: inconsistent with siblings or other crates, or costly to change.
- P3: polish, duplication, dead code.

## P0: Broken
- [ ] 1. `crates/<crate>/src/<file>.rs:<line>`: <problem in one or two sentences, naming the code>. <fix>.
```

Number items in one sequence across all sections, continuing from the highest existing number. Add `Needs a
decision.` where a maintainer has to choose, and `Spans crates.` where the fix touches more than one crate. Group P3
items under short subheadings (Duplicates to remove, Dead code, Types, Errors, Visibility, Splits, Lints).

Then reply in chat with:

- how many findings were added at each priority;
- the P0 items in one line each;
- the three changes that would delete the most code, with rough line counts;
- the proposed `[workspace.lints]` block, if you made one;
- anything you dropped during verification, with one line on why.

## Finishing

The audit is finished when every slice has been read in full, the tool pass has run, every P0 and P1 finding has been
checked against the source, and the tracker is written. If a subagent comes back with gaps, send it back or cover the
gap yourself before writing the file. Ending with a summary that announces the next step is not finishing; do that
step. Stop to ask only if something blocks the work and can't be settled from the code or the guidance files.

## Sources

The checklist draws on these. Read the relevant section when a finding depends on one.

- [Rust API Guidelines checklist](https://rust-lang.github.io/api-guidelines/checklist.html): naming (C-CASE,
  C-CONV, C-GETTER, C-ITER), common traits, C-CUSTOM-TYPE, C-STRUCT-PRIVATE, C-GOOD-ERR.
- [Microsoft Pragmatic Rust Guidelines](https://microsoft.github.io/rust-guidelines/guidelines/checklist/index.html):
  M-PANIC-ON-BUG, M-APP-ERROR, M-LINT-OVERRIDE-EXPECT, M-AVOID-STATICS, M-STRONG-TYPES, M-SINGLE-ITEM-PATH,
  M-UNSAFE, M-CARGO-WORKSPACE.
- [Clippy lint list](https://rust-lang.github.io/rust-clippy/master/index.html) and its
  [README](https://github.com/rust-lang/rust-clippy#clippy) on lint groups (enable `restriction` lints one by one).
- [Rust Design Patterns: anti-patterns](https://rust-unofficial.github.io/patterns/anti_patterns/index.html):
  clone to satisfy the borrow checker, `Deref` polymorphism.
- [Effective Rust](https://effective-rust.com/): types over primitives, `Option` and `Result` transforms, error
  types, `Default` and standard traits.
- [The Rust Performance Book](https://nnethercote.github.io/perf-book/): hashing, heap allocations, `with_capacity`.
- [refactoring.guru smells](https://refactoring.guru/refactoring/smells) and
  [techniques](https://refactoring.guru/refactoring/techniques).
- Workspace lint policies of [ruff](https://github.com/astral-sh/ruff/blob/main/Cargo.toml),
  [oxc](https://github.com/oxc-project/oxc/blob/main/Cargo.toml) and
  [mago](https://github.com/carthage-software/mago/blob/main/Cargo.toml), the closest peers to Pun.
