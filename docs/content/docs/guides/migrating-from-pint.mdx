---
title: Migrating from Pint
description: Convert Pint config, compare formatting results, and update scripts.
---

Start from a clean Git working tree with [Pun installed](/docs/installation). Keep Pint available until you have compared the results.

<Steps>
  <Step title="Convert the config">

```bash
pun migrate --from pint --dry-run
pun migrate --from pint
```

Review migration warnings. Unsupported rules are skipped, so a successful migration alone does not prove equivalent formatting.

  </Step>
  <Step title="Compare the results">

```bash
vendor/bin/pint
pun check --fix
vendor/bin/pint --test
pun check
git diff
```

Investigate differences before switching. `pun check` can also report lint or analysis findings that Pint does not check.

The [recorded parity tests](/docs/parity) compare file contents in separate project copies. The commands above are a project-level check, not an exhaustive parity test.

  </Step>
  <Step title="Update scripts and CI">

Replace Pint commands in your existing Composer scripts:

```json composer.json
{
	"scripts": {
		"lint": "pun check --fix",
		"test:lint": "pun check"
	}
}
```

Replace `vendor/bin/pint --test` in CI with `pun check`. See the [CI guide](/docs/guides/ci).

  </Step>
</Steps>

## What moved where

The [Pint mapping](/docs/migrate/from/pint) lists every upstream fixer, its Pun rule, option translation and dropped rules.
For other configs, use the [migration mapping overview](/docs/migrate/from).

Layout rules become format rules. Risky and code-deleting rules become lint rules. `pun format` alone therefore does not apply the full Pint configuration.

Migration keeps `pint.json` and the Pint dependency. To roll back, restore your scripts and CI commands and review any rewritten ignore comments. There is no `--remove-tools` flag.
