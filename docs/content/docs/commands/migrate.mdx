---
title: pun migrate
description: Move a project onto one pun.toml from pint.json, .php-cs-fixer.php, phpstan.neon and rector.php, with zero behaviour change.
---

```bash
pun migrate                    # on a terminal: a checklist of the configs it found
pun migrate --from pint        # only these (comma-separated: pint, php-cs-fixer, phpstan, rector, mago), no prompt
pun migrate --yes              # everything it found, no prompt
pun migrate --dry-run          # show what it would write, change nothing
```

## Choosing what to migrate

`pun migrate` looks for these in the project root and lists only the ones it finds, each with its file:

| Tool | Files | Migrated today |
| --- | --- | --- |
| Pint | `pint.json` (or `--config`) | yes |
| PHP-CS-Fixer | `.php-cs-fixer.php`, `.php-cs-fixer.dist.php` | yes |
| PHPStan | `phpstan.neon`, `phpstan.neon.dist`, `phpstan.dist.neon` | not yet |
| Rector | `rector.php` | not yet |
| Mago | `mago.toml` | not yet |

On a terminal it shows a checklist with every found config checked; space toggles, enter confirms, Esc cancels. Only
the checked ones are migrated. Without a terminal, under a [coding agent](/docs/guides/coding-agents), with `--yes`
or with `--from`, it never asks: `--from` picks, otherwise everything found is migrated and the output says so.

```text
$ pun migrate --yes
pun migrate: migrating everything detected (pick with --from): pint.json, phpstan.neon, rector.php
pun migrate: pun.toml written from pint.json, ignore comments rewritten in 0 file(s).
  pint.json     migrated
  phpstan.neon  skipped: PHPStan migration is not supported yet; phpstan.neon left untouched
  rector.php    skipped: Rector migration is not supported yet; rector.php left untouched
```

PHPStan, Rector and Mago are listed as "(not supported yet)". If you pick them, the summary says they were skipped and
their config is left as it was. With pint.json and a `.php-cs-fixer.php` both picked, pint.json gives `[format]`, as in
Pint. With neither found, `[format]` gets Pint's default (laravel, or `--preset`).

With no config at all it says "no pint.json, .php-cs-fixer.php, phpstan.neon, rector.php or mago.toml found" and offers
a starter pun.toml (written without asking when there is no terminal):

```toml
[format]
preset = "laravel"
```

The starter's `[lint.rules]` also lists the four risky rules and the eleven code-deleting rules Pint's laravel preset applies, so `pun check --fix` still
matches `pint`.

Pun reads only `pun.toml`, so `pun migrate` is the one place the old configs are read. Migration day changes no behaviour: `pun check --fix` writes the same bytes Pint did, and `pun analyse` reports the same errors PHPStan did.

<Steps>
  <Step title="Read and report">

Reads `pint.json` the way Pint does (`extend`, `--config`, `--preset`), or a `.php-cs-fixer.php` through PHP-CS-Fixer itself. Every rule Pun can't run yet (a custom fixer, a deprecated rule, a rule not ported) and every Finder setting pun.toml has no key for is named on its own line and skipped; the rest is written, and migrate exits 0. Rule options are written under their [Pun names](/docs/configuration/pun-toml#format-rule-options); an option PHP-CS-Fixer would reject stops the migration with PHP-CS-Fixer's own message, as it stops Pint. An error that stops the migration (no config to read, a `pun.toml` that differs, a config PHP-CS-Fixer can't load) exits 2. Planned: `phpstan.neon` with its baseline, and `rector.php`.

  </Step>
  <Step title="Write pun.toml">

`[format]` gets the preset plus only what differs from it. The risky fixers and the fixers that delete or restructure code (`no_unused_imports`, `no_superfluous_phpdoc_tags`, ...) go under `[lint.rules]` at `"error"`, so `pun check --fix` applies them as Pint did. The Finder moves too: Pint's `in`, or the `in()` folders of a `.php-cs-fixer.php` Finder, become `[files] paths`, and `exclude`, `notName` and `notPath` become `[format] exclude`, `not-name` and `not-path`. A `per` or `symfony` preset, and any PHP-CS-Fixer rule set such as `@PER-CS` or `@PHP84Migration`, is expanded into explicit rules over `empty`. Every rule gets its Pun ID (`"imports/ordered"`, `"imports/no-unused"`). Planned: PHPStan levels expanded into the exact rules they ran.

  </Step>
  <Step title="Convert the baseline (planned)">

`phpstan-baseline.neon` becomes `pun-baseline.toml`, under Pun rule IDs.

  </Step>
  <Step title="Rewrite ignore comments">

`// @php-cs-fixer-ignore rule` becomes `// @pun-ignore-file format/<group>/<name>` (planned: `@phpstan-ignore` comments become `@pun-ignore` with Pun rule IDs). See [Ignore comments](/docs/configuration/ignore-comments).

  </Step>
  <Step title="Switch the workflow">

Composer scripts, CI steps, editor settings and pre-commit hooks move to `pun check`. If Laravel Boost is installed, a Pun guideline is added so coding agents call `pun`.

  </Step>
</Steps>

Running it twice changes nothing the second time. Replaced dev dependencies and the old config files stay unless you pass `--remove-tools`, so rolling back is reverting one commit.
